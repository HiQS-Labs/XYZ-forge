# About the Current Project
**Trinity / xyz 3-agent coordination swarm.** A spike for letting Claude Code, Codex, and Gemini work the same codebase concurrently without colliding. The core is `tick` — a small Node CLI backed by a disjoint-files-per-event log under `.tick/` that gives agents soft path-scoped claims, a 2-claim cap, atomic next+claim (`tick take`), heartbeats (`tick ping`), and a read-only auditor (`tick analyze`) that scores per-agent compliance from git history.

Mechanically the protocol is proven: `validate.sh` is **12/12 green**, and Run 3 (2026-06-14) completed all 6 tasks with **26/26 sandbox-app tests passing**, 0 file collisions, and 0 circuit breaks. The open problem is no longer correctness — it's **load balance**. Run 3 hit only **40% work-bounded concurrent-claim time** (bar is ≥50%) because a static HTTP/store split lets the faster agent idle once its lane drains. Run 4 targets that gap.

## 4. Recent Lessons Learned
**Capture insights to improve processes and avoid repeating mistakes.**

1. **Static partitioning starves the fast agent.** A fixed HTTP/store split means once a lane drains there's no work-stealing — Gemini finished early and sat idle, capping overlap at 40%. Mechanics were flawless; the *fixture* was the bottleneck.
2. **One-shot `tick claim` is a best-effort soft claim, not a mutex.** The projection-after-push race is real: an agent can briefly think it won until a peer's earlier-timestamped claim arrives. Agents must re-check before irreversible work.
3. **Measure work-bounded time, not wall-clock.** Run 2's 21h cross-day window made overlap uninterpretable (0%). Bounding the window to active work — plus parked-claim disqualifiers — made Run 3's number honest.
4. **Test-first pays off where correctness is subtle.** The projection sequencing bug (dropped `scope_changed` events) lived in the hardest-to-eyeball code; a test caught it, and earlier tests would have caught it sooner.

## Bonus: Project Scope Outline

> **Note:** This section is a work-in-progress and is being developed as a natural extension of the 4x4 methodology. It is not yet a core part of the framework but is included here as a supplementary tool for teams who want to add more context to their planning.

### 1. Goals
Prove that 3 heterogeneous AI agents (Claude Code, Codex, Gemini) can work one codebase concurrently with zero merge conflicts, zero file collisions, and measurable, sustained parallelism (≥50% concurrent-claim time). Mechanical correctness is achieved; the remaining goal is demonstrated load-balanced concurrency, then a Phase 2 graduation into a real integration.

### 2. Assumptions
- All coordinating agents share one branch (`.tick/` is branch-scoped; cross-branch is Phase 2).
- Agents honestly declare paths — `tick` measures drift but does not yet enforce it.
- Node standard library only; `package.json` is shared and out of scope for every task.
- Time estimate: Run 4 (design + implement + retest + write-up) ≈ 1 focused session (low) to 1 week (high) depending on whether work-stealing or a new fixture is chosen.

### 3. Potential Risks
- **Work-stealing complexity** could reintroduce claim races the 2-claim cap currently prevents.
- **No enforcement** means a real run could drift outside declared paths and only be caught post-hoc.
- **Worktree/branch friction** remains an adoption risk if Phase 2 needs agents on separate branches.
- **Metric chasing** — over-tuning the fixture to clear ≥50% without proving generalizable coordination.

### 4. Long-Term Maintainability
CLI is ~600 lines of JS; correctness concentrates in the projection logic, which is the easy place to break silently — keep the bash test suite (~400 lines) green on every change. Auto-push/local-transport contract and the disjoint-files-per-event model are the load-bearing invariants; document any change to them in RECAP.md. The auditor (`tick analyze`) is the durable artifact reusable across all future runs.
