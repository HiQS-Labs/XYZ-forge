Skills for driving stalled agents

Skills that semi-automate the boring parts of agent supervision and proactively push an agent forward when it stalls, narrates instead of acting, or keeps bringing back the same class of bug. They live in the repo under skills/; each one opens with a "Recite this" block the agent must echo verbatim as its first line — that recital is the tell that the skill actually loaded.

Pick by symptom

Symptom you are seeingSkillWhat it does in one line
Agent is talking but nothing is moving/unstuckBlocking interrupt: freeze the machinery, re-anchor the milestone, take one goal-moving action.
Ambiguous or multi-part problem that needs a full governed pass/workhorseSeven-rung ladder from triage to verified, cross-model-checked execution.
The same bug keeps coming back/whack-a-moleCluster 14 days of churn, find the one root cause, file one umbrella issue.
Are we just fixing bugs? Is the plan still right?/radar21-day SDLC read: flow mix, regressions, release drift, coaching memo.
Clones and worktrees piling up, PRs unlanded/merge-cleanupSequence and land PRs in dependency order, then tear down clean clones safely.

How they chain

/workhorse     ──(stall / repeated non-zero exits)──►  /unstuck  ──(structural root cause)──►  /workhorse
/merge-cleanup ──(third repair attempt refused)────►  /unstuck
/whack-a-mole  ──(files umbrella + Cluster signature)──►  /radar re-scores it every run and is the only
                                                          thing that calls the class "solved"

workhorse and merge-cleanup both carry a tripwire that self-invokes unstuck; unstuck hands back to workhorse when the blocker turns out to be structural. whack-a-mole files the umbrella; radar measures whether it held.

Workhorse

Governed end-to-end problem resolution

Use when: a task is ambiguous, multi-part, or arrives as a wall of text (agent transcript, bug dump, PR review) and you want it worked through without the agent guessing a patch.
Trigger: /workhorse <task>, "workhorse", "tackle this", "work through this problem", "methodical progress".
Source: skills/workhorse/SKILL.md

0. Intake triage & queue           ──► split the dump into atomic P0/P1/P2 items; park the rest
1. Ground truth   (/debug-mantra)   ──► reproduce, trace the fail path, run disproofs first
2. Least mechanism (/ponytail)      ──► YAGNI, stdlib first, extend existing subsystems, shortest diff
3. Governance gate                  ──► AGENTS.md, SOP.md, GUIDING-PRINCIPLES.md, CHANGELOG, ledger
4. Cross-model consensus (/consult) ──► Codex + agy in parallel; surface disagreements, never average
5. Preservation gate                ──► classify Easy / Costly / One-way door; prove nothing is lost
6. Governed execution               ──► minimal diff, run the runnable check, ledger closeout, next item

What makes it proactive rather than just thorough:

  • Anti-downgrade rail. It may not report "Done" if the primary workflow was bypassed or truncated — for example refusing to land PRs, running teardown-only, and declaring victory. It resolves the blocker or reports the exact blocker.
  • Anti-abandonment. Finishing one queue item while others remain is an in-flight state, not a prompt to ask the operator what next.
  • Tripwire to /unstuck. If a batch loop stops reducing queue depth, or tools keep exiting non-zero without a state change, it invokes /unstuck as a blocking interrupt instead of narrating.
  • Orchestrator re-entry. Called from merge-cleanup, jog, a marathon, or /10days, a repair is a checkpoint: it records the outcome and re-invokes the parent with --resume.
  • Fast-track. Trivial, easy-to-reverse work skips the consult rung with a one-line note. Destructive, published, costly, or one-way-door actions never fast-track.

Unstuck

Goal-movement interrupt

Use when: the agent is passive, trapped in narration, halting on a tool exit code, reporting activity without milestone change, overengineering, or reopening settled decisions. It is a mid-flight interrupt, not another planning framework.
Trigger: /unstuck, "we're stuck", "rabbit hole", "stop overengineering", "the cogs are moving but the goal isn't", "get back to the plan".
Source: skills/unstuck/SKILL.md

It also fires on its own. The agent must self-invoke on any of four tripwires, without waiting for the operator:

  • Two consecutive turns to the operator with no observable milestone change.
  • Tool exit-code inertia: a tool exited non-zero and the agent stopped or asked what to do instead of diagnosing.
  • Passive narration: "Waiting for the run to finish…", "Should I continue?", "Let me know how to proceed" on an in-flight task.
  • False completion: about to say "Done" while a core deliverable was bypassed or unattempted.

The governing question is what is the smallest action that changes the original goal's observable state?

1. Freeze the cogs       ──► stop adding helpers, reviews, plans; record goal / milestone / last real movement
2. Re-anchor the goal    ──► one sentence naming the nearest observable milestone ("failing test passes", "PR exists")
3. Test the blocker      ──► "if this were fixed now, could the milestone proceed?" → goal blocker / safety / external / polish / cog
4. Choose one move       ──► execute the accepted plan, fix one narrow blocker, use an existing seam, or ask one crisp question
5. Act, verify, re-drive ──► one action, check the milestone itself, re-launch the primary engine (e.g. --resume), emit the receipt
  • No bandages. Never disable tests, silence lint or type errors, weaken contracts, or patch a call site when the invariant is broken. Structural fixes hand off to /workhorse.
  • Recurrence tripwire. The second time the same class of blocker appears, a narrow fix is no longer the smallest move — escalate to /workhorse, or take the bridge once and label it a bridge.
  • Re-drive the engine. For merge-cleanup, jog, or a marathon, a micro-fix is only the first beat; the interrupt does not exit until the orchestrator is running again.
  • Removes self-created process debt only. It never grants permission to push, publish, delete, spend, or bypass a gate.

Every run ends with a receipt:

UNSTUCK
Goal:     <original outcome>
Stall:    <what was consuming motion>
Move:     <single action taken or exact decision requested>
Evidence: <observable milestone change or named blocker>
Queued:   <genuine blockers filed to durable intake, or none>
Parked:   <non-blocking cogs/polish, or none>
Next:     <one next task state>

Not for a fresh ambiguous problem (/workhorse), an unknown failure (/debug-mantra), or ordinary implementation trimming (/ponytail).

Merge-Cleanup

Worktree consolidation, PR sequencing, safe teardown

Use when: several task clones or worktrees of one repo have accumulated, their PRs are open, and you want them landed in the right order and the folders retired without losing anything or killing a live session. Complies with WORKTREE-SAFETY.md.
Trigger: "Run merge-cleanup on this repo", "Scan all clones and worktrees", "Sequence and merge open PRs", "Tear down clean task clones".
Source: skills/merge-cleanup/SKILL.md · scripts in skills/merge-cleanup/scripts/

0. Primary on-disk checkout  ──► is the operator's own tree clean, on `development`, fast-forwardable? Always first.
1. Discover & inventory      ──► worktrees + sibling clones under safe roots
2. Active session inspection ──► preserve anything with open file handles, driver locks, .tick claims, recent edits
3. Git safety verification   ──► dirty tree, stash, unpushed commits, submodules ⇒ PRESERVE_*
4. PR matrix & toposort      ──► dependency DAG, file-collision pre-check, simulated landing
5. Execute & reconcile       ──► remote squash-merge in order, ff-only the primary, wave_reconcile / releases check / pdda
6. Safe teardown             ──► git worktree remove, clean clones to Trash, prune dangling symlinks

The semi-automation is the drive loop — a script owns the evidence and the repair budget, the agent owns the analysis:

# 1. dry run — Phase 0 + audit + sequence
python3 skills/merge-cleanup/scripts/merge_cleanup.py --primary "$PRIMARY" --prefix XYZ-forge

# 2. fix the primary until Phase 0 says landing-ready
#    (a dirty primary is a blocker to FIX, not a reason to fall back to --teardown-only)

# 3. execute
python3 skills/merge-cleanup/scripts/merge_cleanup.py --primary "$PRIMARY" --prefix XYZ-forge --execute

# 4. exit 3 = handoff / park / defer: read the printed MERGE_CLEANUP_RECORD path,
#    work the caller ladder, then resume — repeat until exit 0
python3 skills/merge-cleanup/scripts/merge_cleanup.py --primary "$PRIMARY" --prefix XYZ-forge --resume --execute

# exit 2 = diagnose first; re-run only once the named gate is fixed
  • Caller ladder on a conflicted PR: /debug-mantra → bounded read-only /recon (8 files, 15 minutes) → /ponytail smallest fix (one repair) → /start-task-style handoff (one repair) → /unstuck when the third repair is refused. Attempts are counted in one record under one lock, so bouncing between rungs or re-cloning never resets the count.
  • Done rule: not "Done" unless Phase 5 ran to exit 0 (or exit 3 was worked and re-driven to 0), or the operator explicitly asked for --teardown-only, --scan-only, or --prs-only.
  • Permission-classifier blocks: if a harness permission layer blocks --execute, retry the identical command once before escalating — a block that passes on a verbatim retry was non-deterministic.

Radar

SDLC process coach and strategic compass

Use when: you want an honest read of the last two to three weeks — are we shipping or firefighting, what keeps breaking, did we regress, is the release plan still the plan. Analysis is read-only; the only writes are the two report sinks, after one confirmation.
Trigger: /radar, /radar --arc, "how is our development cycle going", "are we just fixing bugs", "what keeps breaking", "did we introduce any regressions", "what should we fix once to stop the bleeding", "is the plan still right".
Source: skills/radar/SKILL.md

Three lenses over a 21-day window on trunk:

  • Flow distribution. Commit subjects tallied and proven to sum; the Run / Grow / Transform mix, with Transform counted only when declared via rgt: transform on the governing PROJECT/** doc. Harness machinery is isolated from the denominator.
  • Recurring defects and regressions. Seven evidence signals, a ≥2-days / ≥2-PRs recurrence discriminator, scored targets, plus an open-PR collision check so nothing gets scheduled twice.
  • Release recalibration. Reads releases.db and open milestones read-only, measures orphan-issue share and plan-vs-execution drift. Never tops up the ledger.

The output is a process-coach narrative (wins first, then process friction, then regressions), prioritized coaching action items, cited evidence, and an optional multi-week arc when two or more prior reports exist. It persists to two sinks on one confirmation: an immutable dated RADAR-REPORT-*.md and one live radar-labelled issue checklist with stable target IDs across runs. No targets and no umbrella observations means it writes nothing, on purpose.

Relationship to whack-a-mole: radar re-scores every filed umbrella's Cluster signature on each run and is the only thing that calls a bug class solved — score below 5 on two consecutive runs after the fix merged. Issue closure does not count.

Not for shipped recaps (weekly-shipped), ranking marathon candidates (marathon-triage), maturity assessment (/honest), or executing fixes (/10days).

Whack-a-Mole

Find the bug class that keeps coming back; file one umbrella

Use when: the same bug keeps resurfacing, you have had a run of hotfixes, reverts, or reopened issues, and you want the one foundational defect named and a plan filed to remove it — instead of another symptom patch.
Trigger: "whack-a-mole", "this bug keeps coming back", "we keep fixing the same thing", "what's eating our time", "recurring bugs", "bug churn", "find the root cause behind these".
Source: skills/whack-a-mole/SKILL.md

Pipeline: scan → cluster → score → understand → draft umbrella → approve → file → verify.

  • Scan the last 14 days of issues, merged PRs, fix / revert / hotfix commits, and review threads; detect the repo's own ranking system (PDDA fields, P0 labels, project fields) so the umbrella lands at the top of it.
  • Cluster items sharing two or more independent signals (same hot file, same error string, explicit issue links, same label plus component). One shared signal is "adjacent": listed but not scored.
  • Score churn — reopens ×3, repeat fixes ×3, reverts ×4, cluster size ×1, comments ÷5, days open ÷7 — with raw numbers shown so the ranking is auditable. No cluster above 5 means "no clear pattern"; stop.
  • Understand the top cluster with /debug-mantra and /recon, name the violated invariant, and grade every claim FACT / PATTERN / HYPOTHESIS. "Unrelated bugs sharing a file" is a valid answer and means no umbrella.
  • Draft the umbrella: root cause, symptoms it explains, ordered tasks (reproduce → guard → fix → sweep → verify → document), priority on the repo's own scale, a not-in-scope list, and the mandatory fenced Cluster signature block that radar re-scores.
  • File one issue, only after the operator approves the exact body. It never edits, closes, or comments on existing issues; git is read-only throughout.

Why it matters for stalled agents: an agent that keeps returning with "fixed it again" is usually patching a call site. This skill forces the invariant to be named and the guard to land before the fix, so the next agent has a durable target rather than a fresh symptom.
