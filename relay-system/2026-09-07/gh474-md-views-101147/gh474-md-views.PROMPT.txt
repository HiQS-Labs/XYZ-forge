## Background: what prompted this

`dashboard-staleness-guard.sh` refuses a push whose range writes `releases.sql`/`releases.db`
without moving `ROADMAP-DASHBOARD.md`, when regenerating produces no diff. It classifies by TABLE
NAME against a hand-maintained allowlist that has now gone short twice (GH-315 for `jog_queue`,
tonight for `marathons`/`issue_refs`). Eight ledger tables remain unclassified, so the false
refusals will recur. Issue #474 proposes fixing that properly — the renderer already tracks dropped
rows and warns on stderr, but `--check` exits 0 whenever the output file matches, so the guard is
forced to infer the hazard from table names instead of asking.

## The three options

**A. Remove both MD views, their generators, and the staleness guard.** Closes #474 by deleting the
subsystem that has the bug. Touches all 9 suites, both skills, both governance docs, `hq-lib.sh`,
`githooks/pre-push`.

**B. Keep the views; fix #474 properly.** Give `roadmap-dashboard.sh --check` a distinct
machine-readable result for "rows were dropped", refuse on that, delete the table classifier. Small
diff, one subsystem. Does nothing about churn or merge conflicts.

**C. Untrack the views without deleting them.** `git rm --cached` + `.gitignore`, retire the guard
(nothing committed to go stale), keep the generators so a human or agent renders on demand. Kills
the churn and the conflicts and dissolves #474, but a fresh clone has no dashboard until someone
runs the generator.

1. **Pick one — A, B, or C — and defend it.** If you think the right answer is a combination or a
   fourth option, say so, but name it precisely and price it.
2. **Attack my "decisive fact."** Is "the CLI is documented alongside the file everywhere" really
