### Graded findings

1. **[Must] GH-349 Scope 3 adds inert nullable columns, not maintained modification timestamps.** `_migration_007` only runs `ALTER TABLE ... ADD COLUMN updated_at TEXT`; it neither backfills a value nor installs any mechanism that stamps later inserts/updates (`utils/py/releases_app.py:875-886`). The normal release insert and update paths omit `updated_at` (`utils/py/releases_app.py:2007-2016`, `utils/py/releases_app.py:2047-2069`), as do manifest state changes, including the new unship transition (`utils/py/releases_app.py:2349-2352`). The exhaustive `updated_at` references in this module maintain only the pre-existing `roadmap_items` and `jog_queue` timestamps. The canonical dump also omits the new field from `settings`, `repos`, `issue_refs`, `marathons`, `releases`, `manifest_items`, `doc_lines`, `legacy_lines`, and `grandfather_entries` (`utils/py/releases_app.py:984-1072`), so even a manually populated value would be lost on rebuild. Consequently these columns remain `NULL` and cannot tell consumers when those rows changed, contrary to the migration's own stated purpose at lines 876-880. Implement initial/backfill and ongoing stamping semantics, and preserve the fields through dump/rebuild.

2. **[Should] The GH-351 suite claims exclusivity coverage but never enters either exclusivity branch.** Its only negative transition is a second unship of the same now-`dialed_in` row (`test/gh351-manifest-unship.sh:77-79`). It does not create the reachable same-release case (ship row A, redial the issue into the same release, then attempt to unship row A) or the cross-release case (ship in release A, dial into release B, then attempt to unship A). Those are the two branches implemented at `utils/py/releases_app.py:2325-2342` and explicitly named in the test header at `test/gh351-manifest-unship.sh:8`. Add assertions for `rule=manifest-duplicate` and `rule=dialed-in-elsewhere`, plus state/event non-mutation after refusal.

3. **[Should] The GH-349 suite does not cover all of the scopes it says it covers.** It checks that only two of Migration 007's nine target tables have a column (`test/gh349-vendored-roadmap-ledger.sh:89-94`), but never checks a non-NULL initial value, timestamp advancement after mutation, or dump/rebuild preservation. Its header also promises “Rating system doc / validation” (`test/gh349-vendored-roadmap-ledger.sh:9`), yet after the migration-column assertions the script jumps directly to the unrelated undated-release advisory (`test/gh349-vendored-roadmap-ledger.sh:96-101`). Add behavioral timestamp checks and focused canonical-rating validation (axis mapping/ranges, malformed-token refusal, legacy-vocabulary clash, and `ovr`).
