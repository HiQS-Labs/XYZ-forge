## Definition of Done — what to grade against

Grade every finding `[Blocker]` / `[Should]` / `[Nit]` / `[Pass]`, each with a concrete fix.
The five things most worth your attention, in order:

1. **The migration writer protocol.** `perform_migration()` is a sibling of `perform_write()`, not a
   caller. It brackets `PRAGMA foreign_keys = OFF` **outside** `BEGIN IMMEDIATE`, because SQLite
   ignores a foreign_keys change inside an open transaction. On error it rolls back, restores
   enforcement, and deliberately **leaves the intent journal in place**. Is that bracket actually
   correct and complete? Is there any path where the pragma is not restored, where the journal is
   left when it should not be, or where a partial migration could commit? Note that EVERY registry
   callback must be transaction-safe (no `executescript()`, which COMMITs) — check that claim holds
   for migrations 002, 003 and 004 as written.

2. **Exclusivity and the live-row rule.** Dropping `UNIQUE (release_id, issue_ref_id)` means one
   (release, issue) pair can now hold several rows. Every transition command must select the single
   `state='dialed_in'` row. Is `_live_manifest_item()` correct for every case — including
   cut → redial → cut on ONE release, and an issue that was shipped on release A and is later dialed
   into release B? Does the partial index `ON manifest_items(issue_ref_id) WHERE state='dialed_in'`
   actually express "one release at a time", or does it over- or under-constrain?

3. **The dump grammar round trip.** Six new columns on two tables plus five on a third, all appended
   in fixed trailing order and emitted only when the schema has them (so a pre-migration ledger still
   dumps and digests). `load_dump()` maps legacy `state='open'` to `dialed_in`. `_rebuild()` now owns
   the migration ledger: registry DDL, `load_dump()` skipping `schema_migrations`, then stamping the
   registry versions while PRESERVING each version's original `applied_at`. Can any of this lose data,
   double-load, or produce a ledger that disagrees with the schema it describes?

4. **Baselines.** Auto-capture on `draft → active` only when the manifest is non-empty; empty takes
   NO baseline rather than zero; `active → draft → active` is a silent no-op while the explicit
   `releases baseline` verb refuses. Write-once and all-NULL-or-all-populated are enforced by TRIGGER
   rather than a table CHECK (SQLite cannot add a CHECK in place and rebuilding `releases` — the
   most-referenced table — was judged more risk than the invariant is worth). Are the triggers
   airtight? Is the capture genuinely inside the same writer-locked transaction as the status flip?

5. **The rating grammar's refusal contract.** `rated N/N/N/N` + optional ` ovr N`. The rule is that a
   malformed token is REFUSED BY NAME and never silently read as "unrated". Two token regexes were
   tightened after they fired on ordinary prose (`\brated\s+\d`, `\bovr\s+\S`). Find the
   remaining false positives and false negatives. Also: `calc` is derived at read time and never
   stored — is that actually true everywhere, including `export_timeline.py` and `utils/leaderboard.sh`?

Also in scope, briefly: the exporter's marathon grouping (does it group ONLY rows whose
`marathon_id` names this release's marathon?), the `dialed_in + shipped` denominator, and whether
`utils/leaderboard.sh` really re-derives nothing (the "one scorer" claim).
