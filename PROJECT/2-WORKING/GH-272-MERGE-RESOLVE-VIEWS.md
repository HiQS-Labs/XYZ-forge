# GH-272 · releases-merge-resolve: regenerate + stage derived views

## Status

Spun off from the #260 assessment (improvement item 7). `utils/releases-merge-resolve.sh`
finishes a ledger merge by rebuilding `releases.db` and staging two artifacts (the
`DERIVED="releases.db"` set, lines 124 and 149-154). `ROADMAP-DASHBOARD.md`,
`LEADERBOARD.html`, `RELEASES-PREVIEW.html`, and `LEADERBOARD.md` are untouched, and
`check --rebuild` never refreshes them (`_rebuild` does not call `refresh_preview`; that hook
runs only after write-path commits). On nearly every concurrent merge pair those views stay
conflicted or stale and must be regenerated by hand.

Fix:

- extend the derived set to adopted views; for each view that exists at root or is unmerged:
  take `--ours` in the working tree first (same discipline as `releases.db` — the index stays
  unmerged until regen verifies), regenerate, verify, then stage
- generators (adoption-gated on file presence, mirroring `refresh_preview`):
  `ROADMAP-DASHBOARD.md` → `bash utils/roadmap-dashboard.sh`;
  `RELEASES-PREVIEW.html`/`LEADERBOARD.html` → `python3 utils/timeline/export_timeline.py
  --preview/--leaderboard <path>`; `LEADERBOARD.md` → `bash utils/leaderboard.sh`
- failure posture: hard-fail and leave the merge open (the script's existing refusal
  discipline), not `refresh_preview`'s warn-only
- note: `utils/py/roadmap_dashboard.py` does not exist — the dashboard generator is
  `utils/roadmap-dashboard.sh` (an earlier sketch in #260 named a nonexistent file)
