## System 1 — xyz / `tick` (parallel build)

**Scope used for:** the two genuinely independent halves of Phase 1 — the EventStore
producer (`src/event-store.js`) and the projection+replay consumer
(`deploy/reminders-export/events-projection.js`, `scripts/replay.js`).

**Setup:** runtime extracted self-test **12/12** (byte-exact). Coordinator pinned a shared
event-schema contract (`xyz-tick/CONTRACT.md`) so the two lanes coded to the seam without
reading each other's source. Two lanes seeded, non-overlapping, equal priority:
- Lane A (alpha): `src/event-store.js`, `tests/event-store.test.js`
- Lane B (beta): `scripts/replay.js`, `deploy/reminders-export/events-projection.js`, `tests/events-projection.test.js`

**Measured efficacy:**

|---|---|---|---|

**Honest reading of the two ❌:**
- **Parked-claim flag is a FALSE POSITIVE of the agent execution model.** Both agents *did*
  heartbeat (3 and 4 beats) and worked continuously ~17 min producing 5 files + 17 passing
  tests. The flag fires because a single autonomous subagent **tool call** (write module + run
  `node --test`) runs >10 min wall-clock, and an agent cannot interleave a `tick ping`
  mid-tool-call. The 10-min threshold is calibrated for human-paced windows, not autonomous
  agents with long atomic tool calls. → **Improvement candidate for xyz** (see GH issues).
- **<2 done/agent** is an artifact of a clean 2-lane split (1 each), not a throughput failure.

**Key finding:** xyz delivered a real 90%/zero-collision parallel build — **but only on the two
independent halves.** The genuinely coupled piece (emitting events at `#TransitionReminderState`
in `src/reminders-module.js`) cannot be lane-split; it was deliberately deferred to System 2.
xyz "worked" by carving off the favorable ~60% of the work. **Right tool for independent lanes;
wrong tool for coupled work — exactly as pre-flighted.**

## Cross-system takeaway (so far)

The two systems are **complementary, not competing**: xyz maximizes throughput on
partitionable work; relay maximizes scrutiny on coupled work that needs one consistent hand
plus an independent check. Phase 1 used each for the half it fits — and the seam between them
(the pinned event-schema contract) is what let the parallel halves land without the coupled
piece being ready.

## Cost comparison — point 5 closed (2026-06-16)

_The original feedback gap: the analyzer measured coordination (concurrency, collisions) but
zero cost — xyz and relay could not be compared on cost-per-unit-of-work. Three-phase work
(`COST-OBSERVABILITY-PLAN.md`) added cost signals and produced the comparison below._

**Full comparison:** `PROJECT/2-WORKING/COST-COMPARISON.md` (every number from `tick analyze --format json`).

| Metric | xyz (synthetic fixture, symmetric) | relay (real Gemini turn, asymmetric) |
|---|---|---|
| Tasks done | 4 | 1 |
| tokens_total | 58 920 | 110 008 |
| tokens_per_done | **14 730** | **110 008** |
| human_minutes | 8 | 5 |
| token coverage | 4/4 | 1/1 |

**Reading:** relay used ~7.5× more tokens per done-task. This is expected and honest: relay's
Gemini reviewer ran heavy chain-of-thought reasoning (76 880 output tokens — thoughts-dominant,
not prompt-dominant), while xyz coding turns are short prompts + short completions (~1–2k out).
The systems are not doing comparable work — `tokens_per_done` compares systems-on-their-fit-work.

**Caveats:**
- xyz data is a synthetic fixture (token counts sampled from real session turns); relay data is
  a real live Gemini call. Data provenance is fully documented in `COST-COMPARISON.md`.
- run_type differs: xyz=symmetric (equal lanes), relay=asymmetric (producer+reviewer).
- xyz walltime is fixture-creation time (N/A for real comparison).

**Measurement infrastructure closed:** `tick cost` verb + `parseGeminiStats` + `computeCost` in
`tick analyze` now measure tokens, wall-clock, human-minutes, and cost-per-unit deterministically
with no LLM calls. `gemini-turn.sh` captures tokens automatically after each headless turn
(`-o json` + preamble-skip fix landed 2026-06-16). Point 5 is closed.
