## Background

`PROJECT/1-INBOX/LESS-TYPING.md` captured a Fable 5 web app's read of the operator's Claude Code
prompt log (`~/Documents/Noel Saw/0. Claude Prompts.md`, a CLIO-generated log, 583 `##` entries
across 14 repos as of 2026-07-21) and proposed a 4-step plan to eliminate two repeated manual
ceremonies. This doc verifies that analysis against the raw corpus and this repo's actual tooling,
then turns the surviving recommendation into an executable PDDA plan per the operator's request.

## Verdict on the source analysis

**Concur, with two corrections.**

The repetition claim is real, not sampling noise. Direct corpus counts (583 total `##` entries):
78 lines mention commit+push together, 12+ prompts explicitly say "add ... to marathon" in
distinct phrasings ("add to an upcoming marathon", "add to a marathon file", "add this as a
project to available marathon file", "add the plan into a marathon plan to fire later"), 8 mention
moving docs to `3-COMPLETED`, 6 mention closing GH issues, 5 mention a PDDA sweep, 5 mention
`dry-run`, 22 mention Slack. The staged effort ordering (slash commands today → per-repo manifest
this week → script extraction next → harness integration later) is sound: it validates the
sequence cheaply before touching `marathon_drive.py`.

**Correction 1 — the pre-marathon half overlaps with `marathon-triage`, don't rebuild it.**
`skills/marathon-triage/SKILL.md` already reconciles capture docs against live issue state,
validates preflight contracts, ranks candidates, and forms collision-safe waves — the bulk of the
"pre-marathon" sequence in the log. It also *explicitly refuses to fire a marathon* ("Never execute
the marathon from this skill") — a deliberate safety boundary, not a gap to route around. So
`/pre-marathon` should be a thin wrapper: invoke `marathon-triage`, add the one thing it doesn't do
(sweep stale phase dirs / `ESCALATION.md` leftovers), then a separate confirmed dry-run + fire step.
A from-scratch `/pre-marathon` would duplicate real, working logic.

**Correction 2 — the post-marathon half is a genuine, unclaimed gap.** `skills/marathon-cleanup/SKILL.md`
is archive-only: report-before-mutation, and its scope is reconciling/archiving already-verified-complete
marathon docs — it does not commit, push, open a PR, merge, or close issues. `skills/loose-ends/SKILL.md`
covers generic commit/push/doc-sync but not the marathon-specific PR→merge→pull→close-issues→PDDA-sweep
chain. Nothing in this repo currently automates that chain. This is the higher-value half of the
recommendation and the one to prioritize.

The phased plan below keeps the Fable analysis's structure but reassigns Phase 1's `/pre-marathon`
to wrap existing tooling instead of reimplementing it, and keeps Phase 4 (the harness flag) last,
consistent with the analysis's own effort ordering and this repo's precedent of not touching
`marathon_drive.py` before an idea is validated at the command/script layer.

## Phase 1 — `/pre-marathon` and `/post-marathon` slash commands

- `.claude/commands/pre-marathon.md`: invoke `marathon-triage` for the ranked/preflight-checked
  candidate list, then sweep `PROJECT/2-WORKING` for stale phase dirs and `ESCALATION.md` leftovers
  from prior runs, then `--dry-run` each ready plan and report execution order. Fire only after
  explicit operator confirmation — do not change `marathon-triage`'s no-fire boundary.
- `.claude/commands/post-marathon.md`: commit and push all changed files including manual edits →
  create a PR with notes → merge if green → pull and switch back to `development` → close every GH
  issue resolved by the run → move completed docs to `PROJECT/3-COMPLETED` → run a full PDDA sweep
  → end with `/loose-ends`.

**QA gate:** both command files exist under `.claude/commands/`, dry-run against a real recent
marathon plan and a real recent closeout produces the same sequence of actions the operator
previously typed by hand (spot-check against 3 log entries), and `/pre-marathon` visibly delegates
to `marathon-triage` rather than reimplementing its reconciliation logic.

## Phase 2 — per-repo `loose-ends-sequence.md` manifest

Encode the repo-specific tail (PDDA sweep command, doc folders, gitignore rules) so
`/post-marathon`'s final `/loose-ends` call runs the correct sequence per repo instead of the
operator re-specifying it. Start with this repo (`xyz-3-agents-swarm`) as the reference manifest.

**QA gate:** a `loose-ends-sequence.md` exists for this repo, `/post-marathon` reads it instead of a
hardcoded sequence, and running it against a real closeout matches what the operator's manual
`/loose-ends` invocation previously did.

## Phase 3 — extract `marathon-closeout.sh`

Pull the zero-judgment git ceremony (commit → push → PR → merge → pull → switch) out of the
`/post-marathon` prompt into `marathon-closeout.sh` beside the harness (`utils/` or
`relay-automation/`, matching existing script placement conventions), so it is one command and
usable headless. `/post-marathon` shrinks to "run `marathon-closeout.sh`, then close issues / file
docs / PDDA sweep via the Phase 2 manifest."

**QA gate:** `marathon-closeout.sh` runs standalone (no Claude session) against a real merged PR and
produces the same end state (pulled, on `development`, PR merged) as the manual sequence; a
regression test covers its exit codes.

## Phase 4 — `--post-approve-cmd` harness hook

Wire `marathon-closeout.sh` as an optional `--post-approve-cmd` in `utils/py/marathon_drive.py`,
symmetric to the existing `--pre-advance-cmd` (`marathon_drive.py:58`). When set, a driven marathon
runs the closeout script automatically after the final phase's gate passes, so an interactive
session can start at "review the PR" instead of "do the ceremony."

**QA gate:** `--post-approve-cmd` is documented alongside `--pre-advance-cmd` in
`marathon_drive.py --help`, defaults to unset (no behavior change for existing callers), and a
`test/marathon-drive.sh` case exercises it end-to-end against a stub closeout script.
