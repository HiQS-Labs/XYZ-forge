# Recon Map — LEADERBOARD: the .md stays tracked; only LEADERBOARD.html is retired

Commit: `2e4f8d48` · Mode: grep-only · Lanes: A, B, C, D (serial)

> **This document was rewritten on 2026-09-07 and no longer proposes removing `LEADERBOARD.md`.**
> The earlier version mapped removing the Markdown view, the HTML view and their generators
> together. That plan was adjudicated and split: the **HTML** view is being retired (branch
> `fix/gh474-retire-rendered-html`, gate-green), and the **Markdown** view and both generators
> **stay**. The removal analysis is preserved in git history; it is not the plan of record.

## Subject and change class

Subject: `LEADERBOARD.html` — a rendered HTML view generated by
`utils/timeline/export_timeline.py --leaderboard`.

Change class: **file removal, adoption-by-presence.** Not a subsystem removal — no generator is
deleted and no consumer is rewritten.

Explicitly **out of scope, and staying**: `LEADERBOARD.md`, `utils/leaderboard.sh`, and
`utils/timeline/export_timeline.py` itself.

## Why the Markdown view is no longer part of this

The removal case for both views rested on one claim: that a rendered view is redundant because the
CLI is documented alongside it everywhere. That claim was falsified for the roadmap dashboard
(`AGENTS.md:139-143`, `GUIDING-PRINCIPLES.md:77`, and the `utils/py/router_audit.py` gate), and the
leaderboard was only ever bundled with it by association, never on its own evidence.

The defect that started this (#474) was the staleness guard's **false refusals**, and that has been
fixed at its source — see [recon-roadmap-dashboard-removal.md](recon-roadmap-dashboard-removal.md)
and [recon-gh474-dropped-row-signal.md](recon-gh474-dropped-row-signal.md). Removing a view was
never required to close it.

## Why the HTML view is different, and can go

The two rendered HTML artifacts (`LEADERBOARD.html`, `RELEASES-PREVIEW.html`) are **pure
adoption-by-presence**: every consumer regenerates them only when the file already exists at the
repo root (`utils/py/releases_app.py:1170-1201`, `utils/py/express.py:202-207`). Delete the file and
every consumer simply stops refreshing it. There is:

- no guard on them (`githooks/dashboard-staleness-guard.sh` names only `ROADMAP-DASHBOARD.md`),
- no governance-doc route to them (`ROUTER.md`, `AGENTS.md`, `GUIDING-PRINCIPLES.md` mention
  neither),
- no `router_audit.py` clause requiring them.

That is the entire difference from the Markdown views, and it is why one is a straight deletion and
the other is not.

## State

Read sites: humans opening the rendered HTML. Write sites: `export_timeline.py --leaderboard`,
invoked only when the file is present. Source of truth is `releases.db` (`roadmap_items`); both
leaderboard views are strictly derived, and the Markdown one remains available and tracked.

## Build, failure and rollback

- Build: regenerated by `releases_app.py` after a DB write, and during merge resolution.
- Failure after removal: none — presence-gated consumers no-op.
- Rollback: run the generator and commit the file. Adoption-by-presence makes re-adoption a
  one-command operation, which is what makes this cheap in both directions.
